# Connections, authentication and security

Approved design. Auth mode describes what is sent; storage describes where locally managed credentials live. They are independent.

## Named connections and precedence

`connection add NAME`, `update NAME`, `list`, `show [NAME]`, `use NAME`, `delete NAME --yes`. `add` requires `--base-url`; API version defaults to `v2`, with optional `--api-version v1|v2` and workspace/project/auth/backend defaults. No implicit Cloud destination. Missing explicit/default connection is actionable configuration error, unless all required invocation settings were supplied without a connection.

Settings resolve: explicit flag → nonempty `PLANE_CLI_*` env → selected connection → documented safe default. API version for execution and discovery resolves `--api-version` → `PLANE_CLI_API_VERSION` → saved selected connection → `v2`. Saved explicit v1 configurations remain v1; reject invalid explicit versions rather than defaulting. Never automatically fall back between API versions. Connection selection: explicit `--connection` → `PLANE_CLI_CONNECTION` → saved default. Empty environment means unset. Effective `show` includes each nonsecret value and its source, never token/keyring lookup. Local list/delete/use and logout must remain usable when unrelated URL/timeout env overrides are malformed. New connections resolve `--api-version` → nonempty `PLANE_CLI_API_VERSION` → `v2`, without inheriting the selected connection. Updates retain the stored version unless explicitly changed.

Nonsecret config: `os.UserConfigDir()/foae-plane-cli/config.json`; allow explicit `PLANE_CLI_CONFIG_DIR` for isolated automation/tests. Secrets are separate. No reading repository-local config or automatic Compose migration. Profile names are keys, never path components. Config schema has a version; unknown future versions fail without overwriting. File writes are locked/atomic and preserve unrelated connections.

Environment names: `PLANE_CLI_BASE_URL`, `API_VERSION`, `WORKSPACE`, `PROJECT`, `AUTH_MODE`, `CREDENTIAL_BACKEND`, `TIMEOUT`, `REQUEST_TIMEOUT`, `CA_FILE`, each with prefix `PLANE_CLI_`; secrets use `PLANE_CLI_API_KEY`, `PLANE_CLI_ACCESS_TOKEN`, `PLANE_CLI_OAUTH_CLIENT_SECRET`. OAuth nonsecret client ID, redirect URI, scopes and installation ID can be stored in the connection or supplied via corresponding prefixed env. Never read Compose's `PLANE_*` credentials implicitly.

Base URL is an instance origin plus optional reverse-proxy prefix, e.g. `https://plane.example.net/plane`, **not** a dashboard path or `/api/v1` URL. Append `/api/{version}/...` or `/auth/o/...` while preserving the prefix. Reject query, fragment, userinfo, malformed/ambiguous path and already-versioned API suffixes with guidance. Normalize scheme/host case, effective port and trailing slash, not opaque path content.

## Auth modes

- `api-key`: `X-Api-Key` only. Obtain from selected secret source; missing credentials fail before request with setup guidance.
- `bearer`: `Authorization: Bearer` only, externally supplied access token; no assumed refresh protocol.
- `oauth-user`: registered app authorization-code login and refresh.
- `oauth-bot`: registered app client-credentials acquisition/renewal bound to an app installation.
- `external`: send neither authentication header, do not load a keyring, validate a local token, refresh OAuth or reject missing local auth. Ignore locally available token env values in this mode. Let the configured operator proxy inject credentials; upstream errors remain normal API errors. `auth status` says `externally_managed`, never “authenticated”.

For a local mode, its matching nonempty token environment value overrides the selected stored credential for this invocation only. Reject ambiguous simultaneous token overrides rather than guessing a different auth mode. Selecting the effective destination authorizes sending that environment token there; no additional binding flag or prompt. Overrides are never automatically persisted, refreshed or combined with stored refresh credentials. In OAuth modes an access-token override is externally managed for this invocation; expired overrides require replacement by their owner, not fallback to storage. Changing effective base URL invalidates stored binding; require explicit rebind/login rather than forwarding an old stored token. Credential identity includes connection name, normalized base prefix, auth principal/mode and OAuth client/installation where applicable. API generation alone may share the same credential on the same base; scope/entitlement still belong to the server.

External mode is **not** TLS disablement. Honor standard `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` via `http.ProxyFromEnvironment`; support custom CA via `--ca-file`, appended to the system trust roots. Never log proxy credentials. Accept HTTP or HTTPS endpoints as configured, including LAN/private hosts; no insecure-HTTP flag, confirmation or per-invocation warning. On `connection add` with HTTP, or `update` changing its base from HTTPS to HTTP, emit one informational structured warning. Unchanged updates, API calls, environment overrides and storage transfers do not repeat it. Never rewrite schemes automatically. Out-of-process credential injection and proxy destination policy remain the operator's responsibility, including credentials the proxy adds to unrelated traffic.

## Storage and lifecycle

`file` is the default persistent backend and stores owner-only credentials under the config directory. Opt-in `keyring` uses service `foae-plane-cli` with stable opaque binding keys. Explicit `env` writes no credentials and consumes externally managed tokens only. No silent fallback between backends. A locked/denied/corrupt keyring is an error, not “not logged in”. `auth status` shows mode/backend/binding/expiry and whether the effective token is externally managed; never token values. `auth logout --yes` deletes this connection's local credentials, saved OAuth client secret and pending login state, not remote sessions.

Use 0700 directories, 0600 secret files and locks, safe ownership checks and refusal of symlink/unsafe parent paths for secret writes. Do not follow attacker-swapped links; use dirfd/no-follow primitives where needed. Atomic replacement and locking cover concurrent login/refresh/logout/delete as specified in [architecture](architecture.md#concurrency-and-persistence). File storage is plaintext at rest: disclose this in setup help/schema and once when login first saves a credential, not during ordinary calls or refresh. Keyring selection does not prove a native daemon is available.

`auth login --api-key-file PATH|-` imports a PAT using the selected persistent backend (default `file`); no secret on argv. OAuth login uses the same default, saves access/refresh tokens, expiry and required app credentials, and returns only safe metadata. Explicit `env` with a persisted login is a local configuration error before consent or HTTP, with guidance to choose `file` or `keyring`; it is not an export-only login that cannot renew. Existing token env does not authorize persisting it during unrelated commands. One-time API secret delivery is a separate [output contract](cli-contract.md#secret-delivery): intentional create/rotate/transfer-phase results include the secret in JSON by default, with optional `--secret-output-file`. It does not expose stored login tokens.

Refresh uses the connection-scoped cross-process lock, rereads the bound credential bundle under lock, renews shortly before known expiry (30-second skew), stores rotated refresh tokens atomically and retains the prior refresh token when the server legitimately omits a replacement. Never refresh infinitely or replay an API request after 401. Expired external bearer tokens produce guidance to their owner. Failed renewal sends no API mutation. Invalid/revoked refresh credentials require explicit re-login. A successful rotating exchange followed by local persistence failure is exit 6 with safe recovery guidance, never a claim that the previous refresh token remains valid.

Supply an OAuth client secret through `--client-secret-file PATH|-`, its named environment variable, or the selected backend's existing bound app record, in that order. File and environment inputs together are ambiguous and rejected. Explicit login saves the chosen client secret in that backend so future renewals do not depend on the original environment. Ordinary API calls/refresh use the stored credential bundle, never mix it with a changed environment client secret. Nonsecret app identity stays in connection configuration. Backend migration moves the complete bundle, not just the access token.

Pending OAuth records use owner-only local files even with `keyring`, contain no client secret, and reference a staged app-secret record in the selected backend. Bind them to the connection identity/generation, base, client, redirect, scopes, backend, login ID and expiry. Clean expired records for that connection on login/complete/logout/delete; no background janitor. Keep at most one pending login per connection: a new login invalidates the previous pending attempt. Remove staged secrets on failed/cancelled/expired login without deleting a previously committed credential. Mark a validated callback consumed before its exchange so crashes or concurrent completion never replay a code; failed/uncertain exchange requires a fresh login.

`connection delete NAME --yes` cleans that connection's credentials, pending records and staged secrets before removing its config reference. On cleanup failure retain the reference for repair and report the completed cleanup phases; do not claim transactional rollback. Logout and deletion use stored identities, not unrelated invocation overrides. An in-flight login may commit only if its connection generation and pending ID still match; logout/delete/rebind invalidate them.

## OAuth user login

Official [registration](https://developers.plane.so/dev-tools/build-plane-app/create-oauth-application) and [flows](https://developers.plane.so/dev-tools/build-plane-app/choose-token-flow) require operator app credentials. No shared embedded client secret, hosted broker, undocumented device grant or assumed dynamic registration. Do not treat the MCP server's OAuth proxy as the REST app provider.

`auth login --flow user` uses configured client ID, protected client secret, scopes and exact registered redirect URI:

1. Generate at least 32 random bytes of state; bind to connection/base/client/redirect, one-use login ID and a 10-minute local expiry. Never expose state or authorization codes in debug logs.
2. In local mode bind the exact registered loopback host/port/path **before** presenting consent instructions. A bind failure sends no consent request and leaves no active pending attempt. Use a fixed registered URI, not an unregistered random port.
3. Build `/auth/o/authorize-app/` with `response_type=code`, client ID, exact redirect, space-separated scopes and state. Print deliberate consent instructions/URL on stderr; do not auto-open a browser. Validate GET callbacks, exact state, expiry and single use; reject unexpected callbacks without consuming the valid login. Shut the listener down on completion/cancellation. JSON final output contains only safe login metadata.
4. Exchange once at `/auth/o/token/`, form-encoded authorization_code, code, client_id, client_secret, redirect_uri as documented. Use an isolated HTTP client with redirects disabled, deadlines and reflected-secret suppression. Validate token_type/expiry and persist only after successful response validation.
5. Return safe identity of the connection/backend and expiry; no raw tokens. No requirement to preflight identity after login and no claim that consent guarantees every scope/feature.

Headless mode is explicit `auth login --flow user --headless`: securely persist pending state, emit the consent URL and login ID, then exit 0 with `status:pending`. `auth complete --login-id ID --callback-file PATH|-` consumes the exact full redirected URI, validates its registered destination/state/code and exchanges once. Use an operator-owned registered redirect where the operator can obtain that callback; no CLI-hosted public service is required. The consent URL is intentional output; the completed callback is secret input, never a flag value. Pending state expires after 10 minutes and follows the cleanup rules above. Manual completion does not bypass authorization, fabricate a code or prove that the deployment permits a chosen redirect URI.

PKCE/public-client and loopback registration support are not established by the inspected Plane docs. P02 must inspect further official evidence before enabling a public-client variant. Confidential bring-your-own-app mode is the baseline; report unsupported provider behavior plainly. Do not claim mock acceptance proves that a production registration UI accepts localhost.

## Bot flow

`auth login --flow bot` supports consent installation or a supplied app installation ID. Consent uses the same state protection/pending mechanics; callback supplies `app_installation_id`. Acquire at `/auth/o/token/` with HTTP Basic client_id/client_secret, form `grant_type=client_credentials`, `app_installation_id`, scopes. Parse the documented `access_token` field (despite “bot token” terminology). Renewal repeats the credential grant; it is not a user refresh-token request. Optional explicit installation inspection uses `/auth/o/app-installation/?id=...` and bearer auth; no hidden selection of a workspace from several installations.

## Transport isolation

API, OAuth and object-storage clients have separate policies. Reject redirects on ordinary API/OAuth requests; construct trailing-slash routes correctly. Intercept an operation's documented download redirect and follow it with a separate credential-free storage client. Trust absolute HTTP/HTTPS storage targets supplied by that documented response, on any host/port including private/LAN addresses; no origin allowlist, private-IP prohibition or HTTP opt-in. This trusts the selected server to choose where file bytes go. An HTTPS API may return an HTTP storage URL without warning or refusal. Reject malformed URLs, URL userinfo and non-HTTP protocols; these are protocol/input errors, not transport-security policy gates.

Storage receives only the operation's signed material, never Plane auth, proxy credentials copied into origin headers, or API cookies. Storage redirects are disabled unless the reviewed operation explicitly documents a required redirect phase; that phase uses the same HTTP/HTTPS destination policy, with no automatic replay of an upload body. TLS certificate verification and custom CA configuration apply whenever HTTPS is selected. An explicit HTTP target is not a reason to disable HTTPS certificate validation elsewhere.

Redact auth headers, stored tokens, proxy credentials, signed material and callback values from diagnostics, errors, dry-run and ordinary results. Only declared intentional secret-delivery fields and consent instructions are exceptions on their documented output channels. Server-provided content remains data: never execute it, use it as a shell command or let it override connection/auth settings.
